# Frozen test set: pre-registration protocol (draft, 2026-10-17)

Status: draft written by the orchestrator while the first gate v2 measurement was being analysed. Nothing in it is frozen
yet. It becomes binding when the commit that adds the exercises, the wordings and the tag named below exists, and is then
amended only through `LEDGER.md` entries, never edited in place. The red-team answers collected on 2026-10-17
(`../../notes/red-team-answers-2026-10-17.md`) are to be read before freezing; every objection that changes this protocol
is listed in the section "Objections taken into account".

## 1. Why

Every figure published so far is in-sample: the 25 exercises of `bench/exercises/`, their French wordings in
`bench/scripts.py` and the scoring rules of `bench/score.py` were written by the same people, at the same time, as the
gate they measure, and were run many times while the gate and the prompts were being tuned. The 2026-10-09b run
(195/200 turns correct, 0/926 unverified numbers after gate v1) and the 2026-10-17 run (182/200, 51/842 shown markers
with gate v2) are development figures. The frozen set is the one measurement that may be quoted outside the repository
(the demo of 2026-11-17, a PAGE 2027 abstract).

Rule for Claude (the orchestrator and every subagent): Claude may generate data, run the benchmark and write the
report. Claude does not write a single wording of the frozen set and does not touch `score.py`, `scripts.py`,
`gate*.py` or the system prompts between the tag and the publication of the results.

## 3. Size and the bounds it can support

With n exercises and zero failures at the exercise level, the one-sided 95 % upper bound on the per-exercise failure
probability is 1 − 0.05^(1/n): 11.3 % for n = 25, 4.9 % for n = 60, 3.0 % for n = 100. At the answer level (turns),
turns within an exercise are not independent (same data, same memory, same prompt prefix), so the only honest unit
for a confidence interval is the exercise: cluster bootstrap over exercises, as `run_bench.py` already does, or the
exact bound above when there are zero failures.

Decision: **60 new exercises** (the 20 family × unit × BLQ combinations of a new plan, each with 3 noise seeds), 8
turns each, 3 sampling seeds per configuration. Cost per configuration and seed on the 27B: 60 × 8 × ≈ 12 s ≈ 1.6 h
of GPU. The planned configurations (section 6) fit in two nights.

## 4. Endpoints, defined before the run

Primary, per configuration, with the exercise-level interval:

1. **Shown unverifiable quantities**: with gate v2, markers shown / quantities rendered or typed; with gate v1,
   unverified numbers / numbers in the answer shown. The two are not the same quantity (v1's "verified" means "appears
   in a tool text or the user's message", v2's means "resolved and typed from the structured result"); both are reported,
   neither is called "hallucination rate" without its definition next to it.
2. **Oracle-correct turns**: a turn is correct when every expected value the question asks for is present and matches
   the engine's value under the gate's rounding rule, and no forbidden (computed, converted) value is present.
   **Change before the tag**: the compare turn requires the new-method AUC, the difference and the percentage; it no
   longer requires the old-method AUC to be restated (the 2026-10-17 v2 run lost 12 turns on that requirement alone,
   and the question does not ask for it). The in-sample runs are rescored with the same rule for comparability
   (`run_bench.py --rescore`), and both figures are kept in the report.
3. **Invalid or failed tool calls** / total calls.
4. **Tool-argument audit**: calls whose arguments differ from the script's intent (wrong AUC method, wrong dose, wrong
   route, wrong analysis ids in `analysis_compare`). This is the known blind spot of any number gate: a right number
   from a wrong call. Reported as a rate per call and per exercise.
5. **Time per turn** and prompt tokens of the first call.

Secondary: markers by cause (v2), regeneration rate, OptChat memory calls, recall-turn correctness.

Comparisons between two configurations (v1 vs v2, fork vs upstream, 27B vs 9B) are paired by exercise and seed:
difference of exercise-level rates with a paired cluster bootstrap, and McNemar on turns for the record. No test is
run that is not listed here; anything else is exploratory and labelled so.

## 5. Procedure

1. Write and commit this file. Collect the red-team objections and amend (section 8).
2. Abdou adjudicates the 74 gold decisions; commit `decision/ood/gold.jsonl` with its SHA in the manifest.
3. Abdou and dsh write the wordings; commit `bench/frozen/wordings.json`.
4. Generate the 60 exercises with the new seed; commit with `MANIFEST.json` (SHA-256 of every file, the Caladrius
   build used by `model_simulate`, the generator commit).
5. Tag `frozen-set-v1`. From here on, the files of section 2 are read-only.
6. Run the configurations of section 6 in the order listed, three seeds each, in the background, one configuration per
   GPU session. Every run folder is committed as it finishes (JSON per exercise and `report.md`; the `-data` folders
   stay ignored).
7. Write `bench/frozen/RESULTS.md` from the reports with the endpoints of section 4 and nothing else; exploratory
   findings go to a separate section marked as such.
8. Any deviation (a crash, a rerun, a bug found in the scorer after the tag) is an entry in `LEDGER.md` with the date and
   what was done; the tag is not moved.

## 7. What this protocol does not cover

- Several subjects per exercise, fitting questions, and the 20-tool surface (`fit_run` is still excluded for
  context reasons): out of scope of frozen-set-v1, to be a v2 set.
- Real data: everything is synthetic by the rule of 2026-10-09.
- A comparison with any commercial software.
