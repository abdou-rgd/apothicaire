# Apothicaire v0

## In plain words

**What this is.** Apothicaire is a pharmacokinetics assistant that runs entirely on one consumer PC: a single graphics card with 12 GB, nothing sent to the cloud. You give it a table of drug concentrations over time and ask questions in French or English: what is the half-life, the clearance, how do two ways of computing the area under the curve differ. It does not calculate. A language model (Bonsai 2 27B, a "ternary" model from PrismML) reads the request, calls the Caladrius engine, and explains what the engine returned. Around the model are three parts that are not AI: the Caladrius engine, which produces every number; a deterministic check, `gate.py`, which rejects any number in an answer that is not in a tool result or in the user's own message; and a benchmark, in `bench/`, which measures how often the whole thing fails.

**What this is not.** It is a prototype and an experiment. It is not a product and not a replacement for anything. It must never be used for a real patient or for a regulatory decision. The numbers below come from synthetic exercises simulated by Caladrius, not from patients. They are also thin: one run of each benchmark, one sampling, one model, scripted questions, and a scoring script whose labels I adjusted after reading the first results (the section "Benchmark" lists each change). They are counts, not guarantees.

**Who is building it, and why.** I am Abdallah Ragued. I hold a Master's degree in health data science (Université Paris-Saclay), I am in the Master's programme in pharmacokinetic modelling at Université Paris Cité, and I was a pharmacometrics intern at Sanofi R&D. I want to do a PhD at the meeting point of drug metabolism and pharmacokinetics (DMPK) and artificial intelligence. This repository is where I test the question that motivates that goal: can a small local AI be trusted with pharmacokinetic numbers? The longer story of the author is in the Caladrius README.

**How it fits with Caladrius.** Caladrius is the other half of the project: a calculation engine in Rust whose every output is checked against an independent calculation. Apothicaire reaches it through the Model Context Protocol (MCP), as a list of tools: import a table, run a non-compartmental analysis, read a result, export a table, compare two analyses. The model sees seven tools in all. For the full picture of the system, with a diagram, read the section "In plain words" of the [Caladrius README](https://github.com/abdou-rgd/caladrius) and open `docs/explainer.html` in that repository.

**Why the model is not allowed to calculate.** A language model writes plausible numbers. In my first runs it multiplied, subtracted and converted units by itself, and some of its results were wrong. So the rule is that a number may reach the user only if it was computed by Caladrius or typed by the user, and the gate checks it in plain Python after every answer. If it finds a number that comes from nowhere, the model is asked once to try again, and a warning is shown if the second try fails. The headline results, on 25 simulated exercises of 8 French turns each: with six tools, the gate found 76 invented numbers out of 932 in the first drafts, all in the one question that asks for a difference and a percentage between two areas; once Caladrius had a `compare` command and the model was told to use it, it found 0 out of 926. The model called the tools correctly in 160 of 160 calls, and 170 of 175 turns that expect numbers also passed a second check (`bench/score.py`) that the number is the one asked for. The gate cannot see a right number attached to the wrong parameter, which is why that second check exists, and neither check reads free-text explanations.

**Why OptChat.** A long conversation does not fit in the context of a 12 GB card. OptChat is an idea by Victor Taelin: keep the whole chat on disk and show the model a view in which recent messages are verbatim and older ones are merged into summary lines, arranged as a tree. Nothing is deleted. My prototype of it is published at <https://github.com/abdou-rgd/optchat> (MIT OR Apache-2.0), cloned as the sibling folder `../optchat/`, and Apothicaire imports it unchanged.

**What comes next.** The card `decision/PLAN.md` describes a spike, not finished work: a small decision model (0.8B to 3B parameters) would answer closed questions about the data (which analysis, which route, which AUC method), and a deterministic harness would call Caladrius and write the answer from templates, so that no generated number can exist. The 27B pipeline is kept, and both would run on the same benchmark with the same checks. The first step, a dataset of synthetic exercises, exists; the rest does not.

**How it is built, and what went wrong.** The code is written by AI coding agents (Claude Code, and a DeepSeek agent as a second contributor) under a written contract, with a task board and a human who decides what is published. What went wrong, stated in the sections below: the first demo showed the model converting units wrongly, and moving a unit label in the digest only moved the problem; a preliminary benchmark run exposed a tool schema the model could not fill in; and the label table of the second check was widened after I read the rerun, so its figure is not out-of-sample.

**Sources, tools and credits.** The engine's own sources are in `ATTRIBUTION.md` of the Caladrius repository; the short version for this repository:

- Model and runtime: Bonsai 2 27B and the PrismML fork of `llama.cpp` (PrismML); `llama.cpp` and `ggml` (Georgi Gerganov and contributors).
- Memory: the OptChat gist by Victor Taelin.
- Calculation: Caladrius, reached through the Model Context Protocol (MCP), the open protocol for connecting tools to models.
- Candidates and next step: Underdog Saluki 27B (Conway Research), a model to compare; the `d1` decision models (Liquid AI) and the decision-model recipe (Unsloth).

Reading, and its limits:
- With the prompt change of 2026-10-09 ("quote tool values verbatim, never convert units; if a unit is missing, say so") the model no longer converts CL/F and Vz/F: 1 unit conversion in 932 numbers, against 10 occurrences in 73 in run 2 (different script, so only indicative). What it still does, in every exercise, is the arithmetic it is tempted to do when asked for a difference and a percentage between two AUC; the gate catches all of it, and one regeneration removes it each time (25 / 25). This is one run with one sampling: the 25 / 25 is a count, not a guarantee.
- What each check cannot see. The oracle check cannot see free-text claims or reasoning (an acceptability judgement, an explanation, "the dose has no unit" said in a remark), the route and method words of the recall turn, a value written before its label, or the `not_available` turns, and it reads only the number that follows a label from a closed table of spellings; the gate cannot see a right number on the wrong parameter, from the wrong AUC method or from an analysis run with the wrong options, because every such number is in a tool result. The oracle check was written after the run and its label table and unit vocabulary were fixed while reading these 25 stored transcripts, so its 168 / 175 is not an out-of-sample figure; the 21 tests of `test_bench_oracle.py` use synthetic answers, and it has not been validated on a second run.
- The taxonomy rules are heuristics (`bench/score.py`) and fire by chance on random numbers (about 11 % unit conversion and 11 % misread on random 3-digit numbers, 22 % arithmetic on random 4-digit numbers; the report prints this baseline). The unverified counts never depend on them.
- Single-subject synthetic data, one model, scripted questions (the `compare` turn is built to tempt arithmetic), exercises not shuffled. The scripts and rules were fixed before the run, but three things were changed after seeing results, all in the harness and listed here: (1) a preliminary run of the first 8 exercises (`bench/runs/2026-10-09-prelim-route-anyof/`) showed the 27B writing the infusion route object as a string (6 invalid `nca_run` calls, then a loop on exercise 5), so the schema was changed to `route = iv_infusion` + `infusion_duration` (the client builds the object) and all 25 exercises were rerun; (2) the taxonomy got an arithmetic rule on the numbers written in the same answer before that rerun; (3) after the run, the "says it is not available" patterns were widened because two valid answers ("ne retourne pas", "ne renvoie pas") were rejected, and the 200 turns were re-scored with `run_bench.py --rescore` (2 turns changed, nothing else).
- Not measured: fitting questions (the ground-truth simulation parameters are stored in each `meta.json` for them), longer conversations, other models.

## The number gate

Rule: every number the assistant writes must already be in a tool result (Caladrius) or in a user message (the CSV included). After each final answer `gate.check` extracts the numbers (French and English decimal marks, thousands separators, scientific notation, percentages, units attached) and looks each one up in that set; a number matches an allowed number when the allowed number, rounded to the significant digits written in the answer (at least 2), equals it. So `6,98 %` matches 6.98412 and `7,0 %` too, `6,99 %` does not. **Unit conversions and values computed by the model (differences, ratios, percent changes) are not allowed.** Exempt, not counted: integers 0 to 20 with no unit (counts), years, ISO dates, numbers after a step/label word or a list marker, `#17` message references, bare `10^k`. The assistant's earlier answers and the results of `zoom` / `read_message` are not sources.

In the agent (`Apothicaire._chat_call`): on findings, one regeneration with a `[system reminder]` message appended at the end of the messages (system prompt and tool definitions are untouched, so the cached prefix is intact; it is a `user` role message because chat templates reject a late `system` message) listing the offending numbers and the rule "quote tool values verbatim, never convert"; the better of the two answers is kept; if findings remain, `⚠ n number(s) not found in tool results: ...` is appended to what the user sees. The memory stores the answer without badge or reminder. The turn's stats carry `gate`: counts before and after the regeneration, the findings (number, position, nearest allowed value, power-of-ten hint), the first draft; `run_exo1.py` writes them to the transcript JSON.

Metric: `numbers_unverified / numbers_total`, where `numbers_total` counts the checked numbers (exempt ones excluded), per turn and in total, before the regeneration and in the answer shown.

Known limits, stated plainly:
- The gate is conservative in one direction only. A computed number with 2 or 3 significant digits can coincide with some tool number after rounding (a `−1.00 %` change passed because the tool also contains `1.00`); the counts are a lower bound. A hand review of the transcripts stays part of the protocol.
- It checks numbers, not claims: a right number attached to the wrong parameter or the wrong unit passes (units are read for the exemption rule, not compared with the tool's unit).
- A value the user typed in another format than the tool's is allowed in every plausible reading (`1,234` is 1.234 and 1234).

**Gate v2, typed rendering (experimental, `APOTHICAIRE_GATE=v2`; measured in-sample on 2026-10-17 and 2026-10-18, before the closed renderer below, see `GATE_V2.md`).** The audit of 2026-10-14 showed what set membership cannot see: a right number on the wrong parameter, a changed unit, an inverted sign, a number spelled in words, the small-integer and year exemptions, 2-digit coincidences. In v2 the model does not write tool numbers at all: it writes `{{call_3.cmax}}` (the `ref` shown at the top of each tool result) and `gate_v2.py` replaces the reference with a closed typed assertion read from the MCP `structuredContent` and checked against the tool's `outputSchema`: the engine's value with its sign, its unit and the name of the quantity, `12.3457 ng/mL [Cmax]`. Only the quantities of closed tables can be cited (the NCA parameters, the dose, the selected λz regression, the quality thresholds and named conventions, the `analysis_compare` fields); a raw JSON path or a text field such as an analysis name is never rendered. A bare number must equal, exactly, a number of the user's message; a unit, sign or arithmetic next to a reference (Markdown emphasis included), a unit elsewhere in the sentence or table column that contradicts the engine's, a quantity in words or in Unicode numerals, an unresolvable reference are replaced by a visible marker and listed in a badge (fail-closed), after the same one regeneration with a reminder. What this guarantees: the digits, sign, unit and name printed for a cited quantity are the engine's. What it does not: the words the model writes around them are checked by closed pattern rules, not proven, and a wrong selection (citing `aucall` where `auclast` was asked) is visible but not rejected. v1 stays the default. Spec, resolution rules, guarantees and what remains: `GATE_V2.md`. Tests: `tests/test_gate_v2.py` (synthetic payloads; the audit's blind spots as mutation cases that v1 accepts and v2 rejects; the red-team probes of 2026-10-19 as mutation tests; prefix budget), `tests/test_agent_gate_v2.py` (wiring with the real server). Benchmark: `python bench/run_bench.py --gate v2`.

Two things live outside this repository: the `caladrius-mcp` binary (`APOTHICAIRE_MCP`) and the `optchat` module of the sibling folder `../optchat` (clone <https://github.com/abdou-rgd/optchat> next to this repository). ## Design choices

- **Tools exposed**: `zoom`, `read_message` (memory) + `data_import`, `nca_run`, `analysis_get`, `export_table`, `analysis_compare` (since 2026-10-09, Caladrius commit df87aca: b minus a, relative difference in percent and ratio of the parameters two analyses share, computed by the engine; the system prompt says that differences, percentages and ratios come from it, never from the model). The 20 Caladrius tools do not fit a 12k context; `fit_run` alone is ~3 kB of schema, so fitting is left out of v0. Schemas are flattened (`$ref` inlined) and `nca_run` shows only the options `auc_method`, `start`, `lambda_z`, `quality` (the server still accepts all of them). The route is `extravascular`, `iv_bolus` or `iv_infusion` plus a number `infusion_duration`; the client builds the server's `{"iv_infusion": {"duration": d}}` (the 27B wrote that object as a string when the schema offered it as an `anyOf`: tool-call validity, found by the benchmark). **Static prefix: 2 434 tokens** (system prompt + 7 tools; 2 229 with 6 tools before `analysis_compare`, 2 154 before the 2026-10-09 prompt change and the infusion route of `nca_run`), under the 2.5k budget, cached by llama.cpp.
- **`analysis_compare` is digested too**: one line per parameter, `a 148.923 h*mg/L | b 147.235 h*mg/L | difference -1.6883 h*mg/L | percent -1.13367 % | ratio 0.988663`, the parameters with no value on either side grouped under the engine's reason. `nca_run` called through this client sets no `units` option, so the engine reports no unit in the comparison; the client then labels the units from the worksheet (as for the NCA digest), only when both analyses come from the same worksheet. Nothing is computed or converted.
- **NCA results are digested for the model**: a raw `nca_run` answer is ~17 kB of pretty JSON (7 kB compact: every λz candidate, the profile, ~60 parameters). The client gives the model the same values reorganised: each computed parameter as `"value unit"` (6 significant digits; units labelled from the worksheet column units, `aucpext.*` as %), the names of the parameters not calculated with the reason, the selected λz regression, the options used (auc_method, lambda_z, quality thresholds, BLQ, missing, negative, start), the flags and the engine's `flag_messages`, the `not_calculated_messages` (grouped by identical text) and the worksheet's `unit_warnings` (e.g. `mass_mismatch`, `missing_unit`). No value is converted. The full answer is kept in the tool log and the transcript. Since 2026-10-09 (after the golden tests found them missing) the digest also carries the BLQ / missing / negative / start options, `flag_messages`, `not_calculated_messages` and `unit_warnings`.
- `data_import` also accepts `path` instead of `csv` (the client reads the file); in the demo the CSV is put in the user message by Python and the model copies it into `csv`.
- The digest goes through OptChat unchanged: tool calls and results are logged, summarised and zoomable like any message.

Reading: run 2 was better than run 1 on tool-call validity (3 calls instead of 5, all valid) and **worse on numeric truthfulness (6 distinct wrong values against 1)**: the unit labelling fix in the client moved the problem, from a misread percentage to unit conversions of CL/F and V, it did not remove it. v0 called run 2 "final" on the first metric only; that was the wrong summary. The digest labels units but cannot stop the model from converting them; only the gate can catch it.

Run 3 in one line: with the gate, the 27B still writes the conversions and the computed differences in its first draft (the gate does not stop the model from producing them), and the single regeneration removed them in both affected turns. This is one run: it shows that the loop works, not that the regeneration always succeeds (the code handles the case where it does not: badge, and the better of the two answers is kept). The price is latency (+17 to +21 s on the two affected turns) and the gate's blind spot on low-precision numbers (see above).

Turn 1 costs three LLM rounds (import, NCA, answer) and a long answer at ~24 tok/s; follow-up questions answered from the context take 3 to 7 s. Generation dominates; prompt evaluation stays cheap thanks to the cached static prefix.

## Problems found

1. **Unit conversion by the model is the main hallucination source.** Caladrius only knows the dose unit from a dose column, so with a dose given as an argument CL and V come in `dose unit/(...)` and the 27B converts by itself, wrongly. Fix on the engine side (suggested): a `dose_unit` parameter for `nca_run` (and the fits) so that Caladrius reports CL in L/h and V in L. The system prompt used to say "if you convert them, show the factor", which invited the conversion the gate then has to catch; since 2026-10-09 it says "quote tool values verbatim and never convert units; if a unit is missing, say so" (runs 1-3 above were made with the old wording).
2. **Unlabelled numbers get misread**: without per-parameter units the model took a percentage for an AUC (run 1). Labelling every parameter with its unit in the digest fixed it. Caladrius could return the unit of each parameter itself.
3. The model still does arithmetic itself (differences, percent changes), right or wrong; the gate reports it. Caladrius now has `analysis.compare` (commit df87aca) and Apothicaire exposes it as `analysis_compare` (see the benchmark rerun of 2026-10-09b).
4. Turn 4 of run 2 did not exercise the summary memory (compaction only triggers above 12 raw messages); run 1 did, and the model used Caladrius's own project state (`analysis_get`) rather than `zoom` to recall turn 1, which is a good habit.
5. The old number checker of `run_exo1.py` (a relative tolerance let one wrong value match by accident) is replaced by the gate; the transcripts still end with a hand review.
