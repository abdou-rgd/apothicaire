# Benchmark and demo results

Every measured result of Apothicaire, moved unchanged from the former README: the headline counts, the benchmark of 2026-10-09 and its rerun, and the three demo runs, each with its limits and its dated history.

## Headline

**Why the model is not allowed to calculate.** A language model writes plausible numbers. In my first runs it multiplied, subtracted and converted units by itself, and some of its results were wrong. So the rule is that a number may reach the user only if it was computed by Caladrius or typed by the user, and the gate checks it in plain Python after every answer. If it finds a number that comes from nowhere, the model is asked once to try again, and a warning is shown if the second try fails. The headline results, on 25 simulated exercises of 8 French turns each: with six tools, the gate found 76 invented numbers out of 932 in the first drafts, all in the one question that asks for a difference and a percentage between two areas; once Caladrius had a `compare` command and the model was told to use it, it found 0 out of 926. The model called the tools correctly in 160 of 160 calls, and 170 of 175 turns that expect numbers also passed a second check (`bench/score.py`) that the number is the one asked for. The gate cannot see a right number attached to the wrong parameter, which is why that second check exists, and neither check reads free-text explanations.

**Benchmark headline, two runs of the same 25 exercises x 8 turns (one run each, one sampling, Bonsai 2 27B, gate in the loop), numbers not found in a tool result or user message over the numbers checked, in the first drafts: 2026-10-09 (6 tools, no `analysis_compare`) 76 / 932 = 8.2 %, all 76 in the compare turn (76 / 168 there); 2026-10-09b (`analysis_compare` exposed as the seventh tool, one prompt sentence) 0 / 926, compare turn 0 / 141.** In the answers shown both runs have 0 (0 / 827 and 0 / 926), but the first run needed 25 regenerations to get there and this one none. These numbers are not independent trials (421 of the 926 come from turn 1, and the numbers of one answer share one tool result), so no bound is drawn from them: the unit is the exercise, and 0 failures in 25 exercises give a one-sided 95 % upper bound of 11.3 %. Two runs, one sampling each, in-sample: these are counts. Details, the oracle check and what is open: section Benchmark.

**The same stored answers under the frozen-set rubric** (`bench/runs/RUBRIC-RESCORE.md`, no model run; the rubric of `bench/FROZEN_SET.md` §6.2 also scores the sign, negations, contradictions, table dumps and the acceptability verdict, and asks for the difference and the percentage in the compare turn): 2026-10-09b 191 / 200 turns (195 with the development scorer above), 17 of 25 exercises with every turn correct; 2026-10-17 on upstream llama.cpp 193 / 200 (193), 18 of 25; gate v2, 2026-10-18, 193 / 200 (183), 19 of 25. Still in-sample, and scored against the gold these runs were made with, before CL and V were given in L/h and L.

**Hallucination count (numbers not found in a tool result or in a user message, over the numbers checked, by the deterministic gate `gate.py`): run 3 (2026-10-09, gate in the loop) 0/39 in the answers shown (7/48 in the first drafts, before the gate's one regeneration); run 1 (2026-10-08) 6/44 and run 2 (2026-10-08) 17/73, both re-scored with the gate on the stored transcripts, no gate in the loop.** One scripted conversation per run, one sampling seed: these are counts, not rates with an interval. Tool-call validity and numeric truthfulness are two different metrics; this page reports both and puts the second first.

## Benchmark

The first table is the run of the morning of 2026-10-09 (six tools); the rerun with `analysis_compare` follows the "Reading, and its limits" list.

**25 synthetic exercises x 8 French turns = 200 turns (2026-10-09, Bonsai 2 27B, temperature 0.3, one run, gate in the loop).** Ground truth is simulated by Caladrius (`model_simulate`, proportional noise 5-10 %, fixed seed; pk1 IV bolus / infusion / oral with and without lag / zero-order and pk2 IV bolus / oral; doses in mg and ug, concentrations in ng/mL and mg/L, times in h and min; two BLQ exercises) and the oracle for the NCA questions is Caladrius `nca_run` on the written CSV. Full report: `bench/runs/2026-10-09/report.md` (+ `report.json`, one JSON per exercise).

Primary metric: the hallucination rate of the first two rows (the gate, numbers absent from the tool results). Second line, with its own denominators and never merged with the first: the oracle check (row "oracle check", `bench/score.py`), which catches what the gate cannot, a number that is in a tool result but is not the one asked for.

What the 7 incorrect turns are (the gate cannot see them: the numbers are in the tool results; the oracle check catches all 7 and names the class): ex13 (BLQ, oral) quotes `aucall` (to the last BLQ sample, 3152.57) as AUC(0-tlast) in turn 1 and again in turn 7 (the Caladrius value of `auclast` is 2859.302, last quantifiable point): `wrong_parameter`, 3 numbers; ex07 (BLQ, IV bolus) passes `start: zero` on its own in both `nca_run` calls, so AUC(0-tlast), AUC(0-inf), CL, Vz, MRT and the extrapolated percentage differ from Caladrius's default analysis in 4 turns: `wrong_option`, 10 numbers (the scorer's global search had accepted ex07's CL by coincidence, the oracle check does not); ex21 says in the recall turn that the dose had no unit (it was 5000 ug): `missing_unit`, 1 number. The tool-argument audit (`run_bench.py --tool-arg-audit`, every `nca_run` / `data_import` call against the script's intent) finds 3 deviating calls of 76: the two `start: zero` of ex07 and one `data_import` of ex23 whose CSV is not the exercise's (its answers are correct, so the oracle check says nothing). The 2 invalid calls: a column name with its unit (`time (min)`) in `data_import`, and `analysis_get` with a worksheet id.

Reading, and its limits:
- With the prompt change of 2026-10-09 ("quote tool values verbatim, never convert units; if a unit is missing, say so") the model no longer converts CL/F and Vz/F: 1 unit conversion in 932 numbers, against 10 occurrences in 73 in run 2 (different script, so only indicative). What it still does, in every exercise, is the arithmetic it is tempted to do when asked for a difference and a percentage between two AUC; the gate catches all of it, and one regeneration removes it each time (25 / 25). This is one run with one sampling: the 25 / 25 is a count, not a guarantee.
- What each check cannot see. The oracle check cannot see free-text claims or reasoning (an acceptability judgement, an explanation, "the dose has no unit" said in a remark), the route and method words of the recall turn, a value written before its label, or the `not_available` turns, and it reads only the number that follows a label from a closed table of spellings; the gate cannot see a right number on the wrong parameter, from the wrong AUC method or from an analysis run with the wrong options, because every such number is in a tool result. The oracle check was written after the run and its label table and unit vocabulary were fixed while reading these 25 stored transcripts, so its 168 / 175 is not an out-of-sample figure; the 21 tests of `test_bench_oracle.py` use synthetic answers, and it has not been validated on a second run.
- The taxonomy rules are heuristics (`bench/score.py`) and fire by chance on random numbers (about 11 % unit conversion and 11 % misread on random 3-digit numbers, 22 % arithmetic on random 4-digit numbers; the report prints this baseline). The unverified counts never depend on them.
- Single-subject synthetic data, one model, scripted questions (the `compare` turn is built to tempt arithmetic), exercises not shuffled. The scripts and rules were fixed before the run, but three things were changed after seeing results, all in the harness and listed here: (1) a preliminary run of the first 8 exercises (`bench/runs/2026-10-09-prelim-route-anyof/`) showed the 27B writing the infusion route object as a string (6 invalid `nca_run` calls, then a loop on exercise 5), so the schema was changed to `route = iv_infusion` + `infusion_duration` (the client builds the object) and all 25 exercises were rerun; (2) the taxonomy got an arithmetic rule on the numbers written in the same answer before that rerun; (3) after the run, the "says it is not available" patterns were widened because two valid answers ("ne retourne pas", "ne renvoie pas") were rejected, and the 200 turns were re-scored with `run_bench.py --rescore` (2 turns changed, nothing else).
- Not measured: fitting questions (the ground-truth simulation parameters are stored in each `meta.json` for them), longer conversations, other models.

### Rerun with `analysis_compare` as the seventh tool (2026-10-09b)

Caladrius gained `analysis.compare` (commit df87aca: for each parameter two analyses share, both values with units, b - a with its unit, the relative difference in percent, the ratio, or `not_comparable` with the reason). Apothicaire exposes it as `analysis_compare` (flattened schema, 675 characters; static prefix 2 434 tokens, under the 2.5k budget), digests its answer in the same "value unit" style, one line per parameter, and the system prompt got one sentence: differences, percentages and ratios between two results come from `analysis_compare`, never from the model. Same 25 exercises, same eight scripted turns (turn 7 unchanged: "by how much do the two AUC differ, in value and in %"), same model and sampling, rerun in full into `bench/runs/2026-10-09b/` (`report.md`, `report.json`; the morning run is kept untouched in `bench/runs/2026-10-09/`). The expected-answer rule of turn 7 changed as follows: when the model called `analysis_compare` on its linear and its lin-up/log-down analysis and the result holds the `auclast` row, the engine's difference and percentage are expected in the answer (read from the tool result, and checked against the arithmetic of the ground truth to 5e-5) and allowed together with the ratio b / a; the percentage of the other reference AUC, the inverse ratio and a ratio written as a percentage stay forbidden; without a usable call the old strict rule applies unchanged. The failure taxonomy is unchanged.

|---|---|---|
| **numbers not found in a tool result, first drafts** | **76 / 168** (arithmetic 58, other 16, ...) | **0 / 141** |
| after the gate's regeneration (answers shown) | 0 / 63 (25 of 25 regenerated) | 0 / 141 (none regenerated) |
| the model called `analysis_compare` | not available | **25 of 25 turns**, 30 calls, 30 valid; usable (the two analyses of the exercise, the `auclast` row) in 24 |
| turns fully correct (scorer, rule of the run) | 23 / 25; expected numbers found 46 / 50 | 23 / 25; expected numbers found 94 / 98 (4 per turn: both AUC, difference, percentage) |
| oracle correct (turns; expected numbers) | 23 / 25; 46 / 50 | 23 / 25; 94 / 98 (see the first-pass figure below) |

Whole run: first drafts **0 / 926** (was 76 / 932), answers shown 0 / 926 (was 0 / 827), no regeneration, no badge; taxonomy 0 in every class (was arithmetic 58, other 16, unit conversion 1, unlabelled misread 1); turns fully correct 195 / 200 (was 193 / 200), expected numbers found 552 / 556 (was 496 / 508; the compare turn now expects 4 numbers instead of 2); **tool calls 160 valid, 0 invalid, 0 failed of 160 (was 112 of 114)**, by tool: `analysis_compare` 30, `analysis_get` 52, `nca_run` 52, `data_import` 25, `export_table` 1; oracle check 170 / 175 turns = 97.1 % (95 % CI with exercises resampled 94.9-99.4 %), 549 / 556 numbers = 98.7 % (97.6-99.6 %) (was 168 / 175 and 494 / 508); 10.4 s per turn on average (73 min for the 200 turns), 4 691 prompt tokens on the first call of a turn (was 10.1 s, 4 289).

What is not good in this run, stated plainly:
- **The oracle check was changed after seeing this run.** Its first pass (labels written before the run, `report-oracle-first-pass.md`) gave 159 / 175 turns and 536 / 556 numbers, with 17 of the 20 rejections on the compare turn. I read them: 13 were answers with the right numbers that the label table did not read (the model writes "Valeur absolue" or "En valeur absolue" instead of "Différence", and "contre 76 985 avec la méthode linéaire", the value before the method label); the other 4 are the two failures below. I added those two spellings (`bench/score.py`, with a test per phrasing that fails without the change) and rescored the stored answers with `--rescore`, no model: 170 / 175 and 549 / 556. The scorer's own check and the gate counts did not change. Like the morning's, this is not an out-of-sample figure.
- The compare turn is still not perfect. Two failures. ex12 (infusion): the model called `analysis_compare` six times with a = b = 3 (the same analysis, difference 0) instead of a = 2, b = 3, used its eight rounds, and the "answer" shown is the text of an unexecuted tool call; a new failure mode, the engine accepts the call and the model does not read the zeros. ex23 (iv bolus, minutes): the digest shows the 6 significant digits of a large AUC as `2128760.0`; the model copies `2 128 760,0` (8 digits), which the scorer and the oracle compare at 8 digits with the truth (2 128 757.x): a faithful quote rejected because of a trailing `.0` the digest should not print (fixed 2026-10-09: the digest prints an integral value without `.0`, same rule as `decision/harness.py` through `numtext.py`, tested in `tests/test_digest.py` class `TestIntegralValueFormatting`; no run was rescored).
- The recall turn is at 22 / 25 (was 24 / 25): three answers say the dose has no unit ("500 (unité non reconnue par Caladrius)") although the user wrote 500 mg; same cause as the morning's ex21 (the digest says the dose unit is unknown to Caladrius). Unrelated to the compare tool, but not better.
- ex04 re-ran `nca_run` with `route = iv_bolus` on an oral exercise in the Tlag turn (2 deviating calls of 77 in the argument audit); its answer was correct.
- One sampling per run: 76 / 168 against 0 / 141 is a large difference on 25 conversations of the same script, not an interval; the model was told in the prompt where the arithmetic comes from and was given the tool in the same change, so the run cannot separate the two. The rerun used Caladrius at commit be3625e (the working tree had UI changes of another agent, none in the engine or the MCP server) and 147 tests ([tests.md](tests.md)).

Reading: run 2 was better than run 1 on tool-call validity (3 calls instead of 5, all valid) and **worse on numeric truthfulness (6 distinct wrong values against 1)**: the unit labelling fix in the client moved the problem, from a misread percentage to unit conversions of CL/F and V, it did not remove it. v0 called run 2 "final" on the first metric only; that was the wrong summary. The digest labels units but cannot stop the model from converting them; only the gate can catch it.

Run 3 in one line: with the gate, the 27B still writes the conversions and the computed differences in its first draft (the gate does not stop the model from producing them), and the single regeneration removed them in both affected turns. This is one run: it shows that the loop works, not that the regeneration always succeeds (the code handles the case where it does not: badge, and the better of the two answers is kept). The price is latency (+17 to +21 s on the two affected turns) and the gate's blind spot on low-precision numbers (see [gates.md](gates.md)).


Turn 1 costs three LLM rounds (import, NCA, answer) and a long answer at ~24 tok/s; follow-up questions answered from the context take 3 to 7 s. Generation dominates; prompt evaluation stays cheap thanks to the cached static prefix.
